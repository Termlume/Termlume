# X11 forwarding on Windows

In an SSH connection's properties, enable **Перенаправлять X11 на этот компьютер**.
Connect normally and launch a graphical application from the remote shell. Its
windows appear as separate Windows windows. The SSH server must allow
`X11Forwarding yes` and have `xauth` available to the account.

Settings → X11 controls automatic server startup, Windows/X11 clipboard sharing,
and manual start/stop. Clipboard changes apply on the next X-server start. Close
SSH sessions using X11 before stopping the managed server. The server exits when
Termlume closes. Use X11 only with trusted servers and applications: traditional
trusted X11 clients can access other windows and shared selections.

If X11 cannot be enabled, the SSH terminal opens normally and prints a diagnostic.
For missing `xauth`, install the server's xauth package or allow the account's
preflight check. For rejected forwarding, check `X11Forwarding`, `XAuthLocation`
and server policy. If the local server fails, check its state in settings and
reconnect after starting it successfully. Do not set `DISPLAY` manually: sshd
assigns the forwarded display to the SSH shell.

## Local native preparation

`npm run prepare:x11` downloads SHA256-pinned official VcXsrv 21.1.16.1 and extracts
it into ignored `build/x11`, without running an installer. The normal native build
and Windows packaging preparation also run this step. The first preparation
downloads the 42,993,397-byte installer and 99,727,705-byte corresponding source
archive. Subsequent runs reuse the prepared resources. A local 7z/7za executable
is needed for bootstrapping; the existing electron-builder cache is detected, or
set `SEVEN_ZIP_PATH`. The official pinned full 7-Zip extraction tool stays in the
ignored download cache and is not included with Termlume.

The separate VcXsrv process and accompanying libraries/data are packaged in
`resources/x11`. The GPL license, component licenses and matching source archive
are included; see `native/x11/NOTICE.txt`. Existing VcXsrv installations and user
configuration are not modified.

## Authentication and verification

Each SSH connection receives a fresh 128-bit forwarding cookie. Incoming X11
setup packets are bounded, parsed in either byte order, checked with a constant
time comparison, and rewritten with the managed server's separate cookie before
any data reaches that server. The managed cookie excludes bytes affected by
VcXsrv's Windows text-mode Xauthority reader, retaining over 127 bits of entropy.
Every startup verifies authenticated setup succeeds and unauthenticated setup is
rejected. No `-ac` or `xhost +` is used. Channels use stream backpressure, limited
concurrency and handshake/connect timeouts, and close with their SSH session.

Focused verification commands:

```
npx vitest run --project unit tests/unit/x11-auth.test.ts
npx vitest run --project integration tests/integration/x11-native.test.ts tests/integration/x11-ssh.test.ts
```

On Windows with prepared resources, native tests start the real VcXsrv, map an
`xclock` window, query it through authenticated `xwininfo`, and verify shutdown.
The SSH fixture exercises an actual SSH X11 channel, fragmented setup, successful
native authentication, invalid-cookie rejection and terminal fallback when xauth
is missing or forwarding is denied. These checks do not replace testing against
the particular OpenSSH server and graphical applications used in production.
