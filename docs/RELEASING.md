# Выпуск версии

- `main` — основной канал, включая публичную бету. Внутренние версии вида `0.2.1`, теги `v0.2.1`. Для текущей беты `displayVersion` в `package.json` — `0.2.1b`: это имя отображается в приложении и заголовке релиза. Числовой внутренний номер нужен для совместимости с автообновлением альфа-версий.
- `preview` — предварительные выпуски. Версии вида `0.3.0-alpha.1`. В текущей схеме alpha — предварительный канал, beta — основной.

Обновите `version` в `package.json` и lockfile (`npm version … --no-git-tag-version`), закоммитьте и отправьте нужную ветку. Затем поставьте тег `v` с той же версией и отправьте его:

```sh
git tag v0.1.1
git push origin main --tags
```

Для предварительного выпуска используйте ветку `preview` и prerelease-версию. Workflow проверяет версию и происхождение тега, собирает Windows x64 и создаёт GitHub Release. В релиз попадают установщик, blockmap, манифесты обновлений и SHA-256 суммы. Для локальной сборки: `npm ci && npm run dist:win`.

Не меняйте `appId`, Windows AppUserModelId или каталог `%APPDATA%\Terminal` без отдельной миграции. NSIS не удаляет данные приложения. Клиент не понижает версию при смене канала и запрашивает подтверждение закрытия активных сеансов перед установкой.

Для первой публичной alpha-версии используется тег `v0.1.0-alpha.1`. Внутренние сборки с номером `0.1.0` нужно заменить этим установщиком вручную один раз: автоматический downgrade намеренно запрещён.

Если отправка тега не запустила сборку, запустите workflow Release вручную с нужным тегом в поле `tag`. Перед объявлением выпуска проверьте успешное завершение сборки и наличие установщика и файлов обновления в Releases.

Перед выпуском перенесите пункты из `Unreleased` в раздел `## <версия>` файла `CHANGELOG.md`. Сборка включает описание соответствующей версии в файлы автообновления; приложение показывает его в окне «Что нового».
